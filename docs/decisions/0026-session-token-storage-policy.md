# 0026 — Session token storage policy

Status: accepted

## Problem

Iwara session tokens were persisted as bare plaintext whenever AndroidKeyStore was unavailable: [`TokenCrypto.encrypt`](../../app/src/main/java/io/github/amatsukiichika/iwaram/data/TokenCrypto.kt) returns null on failure and the write path stored the raw value, and [`TokenCrypto.decrypt`](../../app/src/main/java/io/github/amatsukiichika/iwaram/data/TokenCrypto.kt) read every unprefixed value as legacy plaintext. A degraded store was therefore indistinguishable from the pre-encryption format, nothing told the user that the guarantee had been dropped, and a later migration could not tell whether an unprefixed value was old data or a fresh downgrade.
The same restore call ran on the main thread: [`IwaraApp.onCreate`](../../app/src/main/java/io/github/amatsukiichika/iwaram/IwaraApp.kt) invoked the synchronous session restore, which loads the AndroidKeyStore key and runs AES-GCM decryption, while the repository prewarm next to it had already been moved to a background dispatcher. Startup paid an unbounded main-thread cost for a security feature.
Two token sources coexisted: the refresh/access pair owned by IwaraSession, and a manually pasted access token stored by IwaraRepository and pushed into the metadata HTTP client during repository construction. The manual value had no refresh path and no expiry metadata, so its failure semantics differed from the session token it silently overrode.
Certificate pinning was reviewed and does not exist anywhere in the repository. That is not a defect to fix now, but the reasoning had not been recorded.

## Decision

A degraded write is now explicit: TokenCrypto reserves the `plain:` prefix, `sealForStorage` returns either `v1:` ciphertext or a `plain:`-prefixed value with a degraded flag, and it never returns bare plaintext. Decryption strips `plain:`, still passes unprefixed values through as legacy plaintext so existing installs keep their session, and treats an unreadable `v1:` value as null. A null decryption result remains a logout; it never falls back to plaintext.
When a write or migration degrades, IwaraSession persists a boolean `iwara_token_storage_degraded` preference, exposes `tokenStorageDegraded` as a StateFlow, and logs the fact once per process without any token content. The settings screen shows a notice while the flag is set, so the downgrade is user-visible. Legacy and `plain:` values are re-encrypted on the next restore whenever a key becomes available, and the flag clears when the last plaintext value is gone.
Session restore moved off the main thread: `restoreAsync` reads preferences, migrates legacy values and decrypts on an IO coroutine and completes an internal readiness signal. Authentication injection waits for that signal with a three-second bound on the OkHttp network thread (`awaitAccessToken`), while coroutine callers use a suspending wait. The synchronous read entry point keeps its "may be null" semantics, the synchronous `restore` stays internal for tests only, and `isLoggedIn` reports true while a restore is pending if a stored refresh token exists, so the browse screen does not flash a logged-out state.
The three-second bound is deliberate: a healthy restore takes milliseconds and the first metadata request still carries the token, but a wedged Keystore must not hang every API call indefinitely. Requests that hit the bound continue without a token instead of failing.
IwaraSession is the single token owner. The manually pasted token feature was unreachable from the UI, so its repository storage, its StateFlow, the VideoViewModel wrappers and its test were deleted; a residual `access_token` preference is removed once during restore; and that client's token field and repository constructor override are gone. The remaining HTTP client reads the token only through IwaraSession.
The 401 refresh interceptor now retries only when the request body is replayable, meaning absent or not one-shot. A 401 means the server did not execute the request, so method idempotency does not matter, but a consumed streaming body cannot be sent again. Every current caller builds its body from an in-memory string, so the guard changes no existing path; it is recorded as a constraint for future streaming uploads.
Certificate pinning is not implemented. iwara.tv and its file CDN rotate certificates on their own schedule, and a pin that is not coordinated with that schedule turns a routine rotation into an outage for every installed client, with no remote recovery short of a store release. The traffic already uses HTTPS with the platform trust store, which covers the realistic threat model for a public unofficial client.

## Alternatives considered

**Keep writing bare plaintext on Keystore failure** — the old behavior. It keeps login working but is indistinguishable from legacy plaintext, cannot be surfaced to the user, and cannot be cleaned up later. Rejected: a silent security downgrade is worse than a visible one.
**Fail closed: refuse to persist or force a logout when AndroidKeyStore is unavailable** — it would keep the encryption guarantee absolute, but breaks login on a broken ROM or a reset key, which ADR 0002 already rejected as unacceptable for a feature that must not lock users out. The chosen policy keeps the login and makes the cost explicit and visible instead.
**Keep the degraded value in memory only** — the session would disappear on every restart, which is the same as a forced logout, and it still needs a visible explanation. Rejected for the same reason as fail closed.
**Block all API calls until restore completes, without a timeout** — the metadata guarantee would be absolute, but a Keystore fault or a slow disk would hang every request and the diagnostics screen with them. A bounded wait keeps the guarantee in the normal case and degrades to public mode in the pathological one.
**Keep the manual pasted token as a second source with higher priority** — the UI no longer offers it, so it would only preserve dead code, and two storage paths contradict the data-layer rule of one encrypted storage path. Its independent expiry semantics would also keep the override surprise. Rejected.
**Add certificate pinning** — a pinned CDN would protect against a compromised certificate authority, but it converts the provider's rotation into client breakage and adds an operational process this project cannot run. Rejected for now; the review condition is recorded under Consequences.

## Consequences

The normal path is unchanged: a healthy Keystore still stores `v1:` ciphertext and the first metadata request after startup carries the token. On a Keystore fault the user stays logged in, the value is stored as `plain:`, and the settings screen says so.
The explicit prefix makes the two states separable, so a future policy can treat a fresh downgrade differently from pre-encryption data, and the self-healing migration clears the degraded state automatically.
Startup no longer performs main-thread cryptography. Network threads may block for up to three seconds while a restore is in flight, but only during startup and only when the restore has not finished; the request then continues tokenless rather than failing.
The session object now carries restore-readiness state, which outlives a single test. Unit tests reset it through an internal hook rather than through public API.
Removing the manual token feature is a behavior change for anyone who pasted a token in an older build: they are logged out once, their stale preference is deleted, and they log in normally afterwards.
The Robolectric workaround from ADR 0002 is untouched: tests inject a software AES key through TokenCrypto.KeyProvider.
Revisit certificate pinning if a security incident makes certificate authority compromise part of the threat model, or if the backend moves to a certificate or key pin with a documented rotation process and a remote kill switch.
