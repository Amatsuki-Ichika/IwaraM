# 0024 — Gate releases on repository checks, lint, main ancestry and release APK size

Status: accepted

## Problem

The release workflow compared the tag with `app.versionName` bytewise, ran `:app:test`, built and signed the APK, and verified the signing certificate, but nothing else. The comparison had no notion of a version: a malformed tag produced the same generic mismatch as a wrong one, and the error told the maintainer nothing about which side was ahead. It did not run `node scripts/check.mjs`, so the documentation, link, decision-record, tracked-file and APK-size gates that protect every pull request were absent from the one build users install. It did not run lint. It did not verify that the tagged commit belonged to `main`, so a tag pushed on a side branch would publish an unreviewed commit. CI only builds the debug variant, so the `release` entry in `scripts/apk-size-baseline.json` had no consumer anywhere and the release APK could grow without a failing check. The release body was generated from commit subjects described as "squash-merged", contradicting the repository rule that `main` is merged with merge commits and never squash-merged, so the "What's Changed" list could include "Merge pull request #N" instead of authored subjects. When the CHANGELOG had no section for the tagged version — the normal state of a pre-release until its notes are promoted — the body fell back to a generic link even though the pending `[Unreleased]` entries described the release.

## Decision

The release job now runs the repository gates (`node scripts/check.mjs`) after setting up Node 24, runs `:app:lintDebug`, and fails unless the tagged commit is an ancestor of `origin/main`; the check fetches `main` explicitly because a tag checkout is not guaranteed to have that ref, uses `git merge-base --is-ancestor "$GITHUB_SHA" origin/main`, and fails with an `::error::` annotation before any signing material is restored or Gradle starts. After `:app:assembleRelease`, the workflow runs `node scripts/verify-apk-size.mjs`, which compares the built release APK against the committed `release` baseline and its 1% tolerance, making the entry a real ceiling instead of dead data. The release body is the CHANGELOG section for the version, falling back to `[Unreleased]` and then a generic link, plus the APK name and `.sha256`, a compare link to the previous stable tag, and a pre-release note; [0033](0033-pull-request-and-release-text.md) records why. The tag check is version-aware: it rejects a tag that is not `vMAJOR.MINOR.PATCH` with an optional pre-release suffix such as `v0.2.3-rc.1`, validates `app.versionName` against the same shape, and on a mismatch orders the numeric cores with `sort -V` so the error says whether the tag is older or newer; a differing pre-release suffix with the same core is reported as its own case because version sort does not order pre-releases the way semantic versioning does.

## Alternatives considered

**Keep the human pre-tag checklist as the only control.** CONTRIBUTING already asks the maintainer to run `node scripts/check.mjs` before tagging, and every tagged commit reaches `main` through a pull request that CI gated, so the scripted release gates are partly redundant. Rejected because the checklist is memory rather than evidence: the workflow is the only thing that proves the gates passed on the exact commit and artifact being published, and a missed manual step ships silently.

**Rely on CI's debug run for tests, lint and size.** CI already runs the unit tests, `:app:lintDebug` and the debug size ratchet on every pull request. Rejected because the release differs from the pull-request build in ways CI never sees: release signing, release packaging and the release size baseline. A regression that only appears in `assembleRelease` would ship with no check, and "it passed on the pull request" is not evidence about the APK users download.

**Trust branch protection for the main-ancestry requirement.** `main` is protected, so a tag on a side branch is a mistake rather than an attack. Rejected as the only control because branch protection says nothing about tags: a tag can point at any commit, and the mistake it permits — publishing a build of an unreviewed commit — is exactly the failure a release gate exists to catch.

**Update the size baseline inside the release job.** Recording the freshly built size would always pass. Rejected because a ratchet that measures and then accepts its own measurement can never fail; the baseline is a reviewed repository file, and changing it must be a pull request with a stated reason.

## Consequences

A release takes a few minutes longer: Node set-up, the repository gates, lint and the size comparison run before publication, and the workflow now depends on the Node version staying aligned with CI. The ancestry check hard-codes `main` as the release branch; renaming the branch requires updating the refspec and the error text, and a rewritten `main` history (blocked by branch protection and forbidden by the workflow rules) would make older tags fail the check. A release whose APK grows past 1% of the recorded baseline fails until the baseline is raised by a reviewed pull request, so a legitimate size increase has to be recorded before tagging. Release tags must keep that shape, pre-release suffix included; a differently formatted tag now fails before Gradle starts. The gates deliberately duplicate CI: the release job is the last line of defense, not a shortcut, and a gate that fails in both places fails the release before anything is published rather than after.
